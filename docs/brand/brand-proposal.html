2. Proposal: three directions

Shared principles: gold is never used as small text; every text pairing is at least 4.5:1, graphics and control borders at least 3:1; one tokens source (the CSS variables in globals.css) feeds wordmark, favicon and OG card; the OG route keeps hex literals only because Satori cannot read CSS variables, so the build script/tokens should be the single place those hex values come from.

A. Marigold and Plum (refine)

Keeps the cream/plum/marigold-knot equity already in product, but fixes the one structural flaw: gold was used as TEXT. Gold becomes a darkened mark colour and a separate darker text gold. Lowest migration cost; reads as soft, airy, bridal pastel for sangeet / mehendi / haldi browsing.

Type: display Fraunces, 'Iowan Old Style', Georgia, serif; body Inter, system-ui, 'Segoe UI', Roboto, sans-serif. Fraunces + Inter are already bundled via next/font (no new font).

3. Recommendation

Direction A (Marigold and Plum, refine). It fixes every current AA failure that is caused by the palette (gold-as-text, hairline inputs, hard-coded badge) while keeping the equity of the knot mark, plum CTAs and the already-bundled Fraunces/Inter. Directions B and C are stronger visually but are a rebrand, which the evidence (no user research) cannot yet justify.

Trade-offs

  • A: lowest risk, least differentiation from other pastel wedding sites.
  • B: strongest ceremonial identity and no font downloads; highest recolour surface and the red/maroon family is crowded in Indian wedding retail.
  • C: most distinctive; teal clashes with some product photography (green/blue outfits) and discards the marigold story.

What would change if A were adopted (files/tokens only; nothing done)

  • frontend/app/globals.css: add --gold-mark and --gold-text; set --muted-foreground to #665955; raise --border/--input to #857870 (keep a separate decorative hairline token); add dark-mode primary #D9BE82 and wire a theme switch only if desired.
  • frontend/tailwind.config.ts: map the new tokens; deprecate champagne / champagne-deep / sage-text for text.
  • frontend/components/Logo.tsx: wordmark 'Maitri' uses gold-text, mark uses gold-mark.
  • frontend/public/brand/mark*.svg, favicon*.svg, app/icon.svg: stroke #B99A5F to #8F6F2E.
  • frontend/app/opengraph-image.tsx: hex literals for knot, 'Maitri', tagline.
  • components/chat/OutfitBoard.tsx: owned badge #E8A33D with white text becomes token + ink text; 9px primary/80 badge raised in size or opacity.
  • components/DemoBanner.tsx, components/chat/MessageList.tsx, MessageBubble.tsx, components/landing/OccasionChips.tsx: champagne border/text usages.
  • frontend/e2e and component tests asserting class names (e.g. StreamNotice.test.tsx) if tokens are renamed.

Migration risk

Low-medium: colour-only, no layout change, but gold darkens from #B99A5F to roughly #8F6F2E so the brand reads warmer/heavier; OG image caches on WhatsApp/social persist for days; shared hex duplicates (OG route, SVG files) can drift if not generated from tokens.

Screenshots / rule 15c plan

Before/after screenshots of landing, chat empty state, outfit board, saved looks, error banner and the OG card (light only, since dark is not toggled today), committed under reports/screenshots/<pr>/ on the adopting PR's branch and embedded via raw.githubusercontent.com URLs. A contrast unit test over the token hex values should gate CI (extends rule 15b/70a gate 5).

4. Honest limits

  • No user research: preference between directions is a judgment, not evidence.
  • Contrast is computed from hex values, not user-tested; WCAG ratios do not capture thin Fraunces strokes, sunlight glare, or colour-vision differences.
  • Fonts: Fraunces/Inter are not loaded here (offline page), so renders use fallback fonts; Palatino/Georgia availability varies by OS.
  • Alpha utilities were composited over the assumed background; real stacking (images under badges) was not measured. Partner-brand pages were not checked.
  • Logo marks in B and C are quick sketches, not designed marks. Only usages found by grep of app/ and components/ were listed; dynamically built class names could be missed.
  • The 'known 2.49:1' claim was re-derived here, see Section 1.
