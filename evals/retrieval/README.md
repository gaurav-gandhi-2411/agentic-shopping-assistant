# Retrieval eval for Wave 1b V4 (reranker decision)

Purpose: decide which reranker variant to ship, on the same 60 queries and the same top-20
candidate pools:

- **A** the current production LLM reranker (real `src/agents/reranker.py::rerank`, 150 max_tokens),
- **B** no reranker (hybrid RRF order),
- **C** a compact reranker (numbered one-line candidates in, comma-separated numbers out).

Metrics: nDCG@5 and precision@5 on the 5 cards the user would see (precision at labels >= 1,
>= 1.5 and >= 2), bootstrap 95% CIs (10,000 resamples over queries, seed 42), paired differences
A-B, C-B, C-A with CI plus sign and Wilcoxon p, tokens per call and latency p50/p95.

## Label provenance (read this before quoting any number)

**The relevance labels are LLM-consensus labels from three model families (gpt-oss-120b and
qwen3.8-27b via Groq, Claude via packets), not human ground truth.** Label = strict-majority of the
three judges; with no strict majority (for example 0/1/2) the item is flagged as a tie and
resolved by the median for the primary metric, with a sensitivity run that excludes tied items.
Agreement is reported as pairwise Cohen's kappa (unweighted and quadratic-weighted), Krippendorff's
alpha (ordinal, bootstrap CI), confusion tables and per-judge label distributions. Judges see the
title, price, category, colour and a 150-char description in a per-(query, seed) shuffled order;
they never see the store, the system rank, the catalogue gender column or the variant. Stage 2
uses only gpt-oss-120b and qwen3.8-27b on Groq; the primary model gpt-oss-20b is never a judge.

## Query set (60 frozen fixtures: `evals/fixtures/retrieval/q01..q60.json`)

Generated by `make_queries.py` (seed 42), committed so the set is frozen
(`tests/test_retrieval_eval_run.py` fails if the generator and the fixtures diverge). Case i has
occasion = i mod 12 and gender slot = i mod 5, which are coprime, so every (occasion, gender-slot)
pair occurs once. Phrasing style and budget are balanced lists shuffled with `Random(42)`.

| axis | counts (n=60) |
|---|---|
| occasion | sangeet 5, haldi 5, mehendi 5, wedding_guest 5, reception_cocktail 5, office_formal 5, festive_diwali 5, casual_daily 5, college 5, date_night 5, travel_party 5, accessory_footwear 5 |
| gender | women 24, men 24, either 12 |
| budget (INR, in the wording) | none 12, under 1000 12, under 1500 12, under 3000 12, under 5000 12 |
| phrasing | plain English 12, English + Hinglish words 12, romanised Hinglish 12, typo/keyword 12, stylist-style descriptive 12 |
| hard (multi-constraint) | 12 (20%): colour AND budget always, half also carry a style term (`indo-western`, `fusion`) |
| with a colour | 35 |

Each fixture: `id, text, language_style, occasion, gender, budget_inr, hard, constraints
{gender, colour, category, max_price, style_term}, notes`. `constraints` is used only by the judge
rubric. The query text is public product wording (it is sent to LLM judges); no personal data.
Known limitation: a few low-budget cases keep a high-end garment when the occasion has no cheaper
garment in the table (for example women's reception gown/saree), so they may return few candidates.

## Candidates (`candidates/q*.json`, 0.92 MB, committed)

`candidates.py` drives the real compiled LangGraph agent (intent parsing, filters, hybrid RRF with
the gender/colour/price pushdown, kids/fabric exclusion, store diversity, per-store cap) and
captures `(query, candidates)` at the `rerank()` call; no reranker LLM is invoked. Candidates come
only from the 38 public stores in `public_stores.json` (temporary until the store registry,
PR #106, merges): every other store is added to the retriever's inactive-store set, which is
pushed into the BM25 and FAISS fetch (not post-filtered). Outfit-route queries never call
`rerank()`; for those the `search` node is called with a plain search plan (`route:
"forced_search"`, 4 cases: q05 q10 q15 q25). Provenance and per-case counts: `candidates/_summary.json`.

Three queries (q46, q56, q59, all romanised Hinglish) return no candidates because production's
`_is_unrecognized_query` guard sends them to clarify; stages skip them (n = 57 with candidates).
24 more cases return 1-19 candidates (tight gender/colour/price/category filters); 33 return 20.
Four of those have <= 5 candidates (1, 2, 3 and 5): production skips the reranker for them and all
three variants show the same cards (they add nothing to the A/B/C contrast; keep them for coverage).

## Variants

- **A**: `variants.run_variant_a` calls the production `rerank()` with a recording LLM, so the prompt
  (system + candidate block), `max_tokens=150`, `temperature=0` and the production parser and
  fallbacks are exactly production's. Records raw output, finish_reason, cap hit, outcome
  (`ok / partial / parse_error / timeout / no_llm_call`) and the final top-5.
  Difference from production: the live adapter has no model-fallback chain (see "Truncation").
- **B**: RRF order.
- **C**: `variants.build_compact_prompt`: candidates numbered 1..N, `title (12 words) | price band |
  colour`, instructions first (byte-stable prefix), answer = 8 comma-separated numbers, `max_tokens =
  200`, `temperature 0`. The cap is 200, not the ~48 the visible answer needs, because gpt-oss
  hidden reasoning counts against `max_tokens` even at low effort (production's 150 cap is hit by
  8 of 15 reranker calls for that reason). Stage 2 must read `finish_reason` and
  `completion_tokens` from the ledger and raise the cap if any C call hits it. The compact system
  prompt is ~150 tokens, below Groq's 1,024-token minimum cacheable prefix, so caching cannot help C
  as designed. Invalid or short output falls back to (or is topped up from) RRF order.
  C does not replay production's colour-diversity swap (`_enforce_colour_diversity`), A does.

Not replayed for any variant (variant-independent, and the pool is already deduped): graph.py's
post-rerank name+colour dedup, beach per-type cap and price re-sort.

### How truncated reranker output is parsed today (architect item c)

`src/agents/reranker.py:170` calls `llm.generate(..., max_tokens=150, temperature=0)`;
`_parse_selected` (lines 122-145) does `json.loads` on the whole text, else on the first
`{...}` match found by a lazy regex that needs a closing brace. Then (lines 177-181):
`indices is None` -> log `parse_error` -> **return `items[:5]` = retrieval (RRF) order**. There is no
partial salvage: the output is `{"selected": [...], "reasoning": "..."}`, so a cut inside the
reasoning string or the list has no closing brace, parses to None, and the user gets RRF order even
though the picks were already visible in the cut-off text. Only a *valid* JSON with fewer than 5
distinct valid indices is "partial": the LLM picks first, then retrieval order fills (lines 186-194).
If the model spends the whole cap on hidden reasoning and returns empty content,
`GroqClient._chat_one` (`src/llm/client.py:412-425`) returns None, `chat()` moves to gpt-oss-120b
and qwen with the same cap (lines 444-452) and finally returns `LLM_BUSY_MESSAGE` (line 457), which
is not JSON -> same `parse_error` -> RRF order. So in production a cap hit means variant B for that
turn. Pinned by `tests/test_retrieval_eval_variants.py` (`test_truncated_json_falls_back_to_retrieval_order`,
`test_cut_inside_selected_list_also_falls_back`, `test_empty_reasoning_exhausted_output_falls_back`,
`test_complete_json_reorders_and_closed_short_list_is_topped_up`). How often it happens: the V4
report counts 8 of 15 gpt-oss-20b reranker calls at 150 completion tokens
(`reports/wave1b/v4-token-breakdown.md` line 43); my recount of
`reports/wave1b/v4/log_analysis.json` (turn rows, model 20b, input >= 1500) gives 9 of 17
(command: a short script over `turns[].in/out/models`); the filters differ and were not reconciled.
`finish_reason` is not logged, so "at cap" is inferred from `completion_tokens == 150`.

Outputs go to `reports/wave1b/v4e/` (untracked): `ledger.jsonl` (per-call usage: prompt, completion,
reasoning and cached tokens, latency, rate-limit headers), `cache.jsonl` (resumable; keyed by
(judge, query_id, prompt_hash), a rerun makes no duplicate calls), `labels_<judge>.json`,
`variants.json`, `report.json`, `plan.json`. `--resume` is the default behaviour.

### Judge flow and the calibration gate

1. Each Groq judge labels the 20 calibration items (4 synthetic queries x 5 hand-labelled
   candidates, built from the rubric: wrong gender or category = 0, exact match = 2, one colour miss
   or a <= 25% budget overrun = 1). Pass criterion per judge: >= 18/20 exact and none off by two; the
   harness refuses to continue with a judge that fails and says so.
2. Claude labels the same calibration packet. Across all three judges the harness computes pairwise
   kappa (unweighted and quadratic) and Krippendorff alpha. **If any judge pair has kappa < 0.4 it
   stops before the main run and prints the confusion tables and the rubric.** With fewer than three
   judges' calibration labels it also stops (`--allow-partial-gate` overrides, for debugging only).
3. Main run: one call per query with all candidates (cap 1,500 tokens incl. hidden reasoning),
   `reasoning_effort` low for gpt-oss, `temperature` 0, `seed` 42. qwen3.8-27b is sent
   `reasoning_effort: "none"`: UNVERIFIED for this preview model; a 400 from the first call stops the run.
4. Optional: re-judge a random 10 queries with a different shuffle seed to measure stability.

## Quota and day plan (stage 2)

Architect limits, built in as defaults (`common.py`): judges gpt-oss-120b and qwen3.8-27b only;
daily token budget 150,000 per judge model (hard stop, counted from the ledger per UTC day);
the reranker model gpt-oss-20b has a separate 100,000 tokens/day budget because prod canary
traffic already uses ~100K of its 200K TPD; at most 1 request per 8 s per model; stop after 3
consecutive 429s; Retry-After and `x-ratelimit-remaining-tokens` honoured. Provider limits as
briefed: 30 RPM, 1K RPD, 8K TPM, 200K TPD per model.

Token estimates from the built prompts (`python -m evals.retrieval.run --stage plan`, tiktoken
`o200k_base` as a proxy; for qwen the real tokenizer differs, so treat qwen as +-15%; n = 57 queries
with candidates; completion tokens are ASSUMED, not measured: judge 400, A 150, C 100, replace with
ledger medians after the first calls):

| prompt | mean tokens (prompt) |
|---|---|
| judge (rubric + 20 candidates) | 1,511 (max 1,931) |
| calibration judge call (5 candidates) | 658 |
| A production reranker (system + user) | 1,649 |
| C compact reranker (system + user) | 542 |

| model | work | tokens (expected) | daily budget | days |
|---|---|---|---|---|
| gpt-oss-120b | calibration 4.2K + 57 judge calls 108.9K + caching probe 5.4K | 118.6K | 150K | 1 (2 if every call hits the 1,500 cap: worst case 181K) |
| qwen3.8-27b | calibration 4.2K + 57 judge calls 108.9K | 113.2K | 150K | 1 (2 in the worst case) |
| gpt-oss-20b | A 57 calls 102.6K + C 57 calls 36.6K + caching probe 5.4K | 144.6K | 100K | 2 (A alone exceeds one day: split across days; the cache resumes) |

Optional judge self-consistency (10 queries) adds ~19K per judge. The 8K TPM limit is the binding
rate: ~1.9K tokens per judge call means ~4 calls/min, about 14 minutes of wall clock per judge for
the main run (the 8 s spacing alone would be ~7.6 min). Caching probe: 3 calls on each of
gpt-oss-20b and gpt-oss-120b (6 total), verdict from `cached_tokens` and the TPM-header deltas,
refill-corrected; run it before stage-2 prompt design.
