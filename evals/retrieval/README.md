# Retrieval eval for Wave 1b V4 (reranker decision)

Purpose: decide which reranker variant to ship, on the same 60 queries and the same top-20
candidate pools:

- **A** the current production LLM reranker as deployed (real `src/agents/reranker.py::rerank`,
  gpt-oss-20b, 150 max_tokens, reasoning low),
- **A2** the same reranker with the truncation fixed (cap 600; a `finish_reason == "length"` is
  never trusted, it falls back explicitly to retrieval order and is counted),
- **B** no reranker (hybrid RRF order),
- **C** a compact reranker (numbered one-line candidates in, comma-separated numbers out).

Two factors are run on the best two arms (highest nDCG@5 point estimate): **F1** single-garment sets
demoted vs not (ethnic-wear queries), **F2** gender-unspecified queries, current order vs
gender-interleaved. A and A2 are also run twice per query (N = 2: rep 1 plus one repeat) to
measure **card-count stability**. The A/A2/B/C comparison runs on candidate pools **regenerated on
current master** (`candidates_master/`, see "Candidates"); the pre-#129 frozen pools are judged and
serve as the "sets not demoted" arm of F1.

Metrics: nDCG@5 and precision@5 on the 5 cards the user would see (precision at labels >= 1,
>= 1.5 and >= 2), bootstrap 95% CIs (10,000 resamples over queries, seed 42), paired differences
(A-B, A2-B, A2-A, C-B, C-A, C-A2) with CI plus sign and Wilcoxon p, tokens per turn, latency
p50/p95, the rate of `finish_reason = length`, the parse-failure / fallback rate, and how often
card counts differ between repeats.

Stage 2 also contains a consensus relabelling of strict-gold labels, see "Consensus
relabel" below. **Live calls so far: stage-2 day 1, calibration only (8 Groq calls), see "Stage 2
log".** Nothing else has been run live.

## Label provenance (read this before quoting any number)

**The relevance labels are LLM-consensus labels from three model families (gpt-oss-120b and
qwen3.8-27b via Groq, Claude via packets), not human ground truth.** Label = strict-majority of the
three judges; with no strict majority (for example 0/1/2) the item is flagged as a tie and
resolved by the median for the primary metric, with a sensitivity run that excludes tied items.
Agreement is reported as pairwise Cohen's kappa (unweighted and quadratic-weighted), Krippendorff's
alpha (ordinal, bootstrap CI), confusion tables and per-judge label distributions. Judges see the
title, price, category, colour and a 150-char description in a per-(query, seed) shuffled order;
they never see the store field, the system rank, the catalogue gender column or the variant.
**Store names are scrubbed from titles and descriptions** (`scrub.py`: every slug, display name
and domain label in `src/config/store_registry.py`, public and non-public, removed before the
150-char truncation): before the scrub 222 of 961 candidate lines (23.1%) carried a store name
(vastramay 74, tjori 46, kisah 34, jadeblue 23, ...); after, 0 of 961
(`python -m evals.retrieval.scrub`, which also prints the before/after; the leak detector is
independent of the scrubber and `tests/test_retrieval_eval_scrub.py` checks every registry store).
Brand names that are not registry stores (for example "YASH GALLERY" inside a title) are not
scrubbed. Stage 2 uses only gpt-oss-120b and qwen3.8-27b on Groq; the primary model gpt-oss-20b is
never a judge.

## Variants

- **A**: `variants.run_variant_a` calls the production `rerank()` with a recording LLM, so the prompt
  (system + candidate block), `max_tokens=150`, `temperature=0` and the production parser and
  fallbacks are exactly production's. Records raw output, finish_reason, cap hit, outcome (see
  "Outcome taxonomy" below) and the final top-5.
  Difference from production: the live adapter has no model-fallback chain (see "Truncation").
- **A2**: `variants.run_variant_a2`: variant A with the cap overridden to `A2_MAX_TOKENS = 600`
  (`CapOverrideLLM`, so `rerank()` itself is not forked: same system prompt, candidate block, parser,
  partial top-up and colour-diversity swap; `reasoning_effort` low). **Cap, from the day-1 variant A
  ledger (53 live calls, cap 150):** the 22 calls that finished used 22-107 reasoning tokens
  (median 77) and 26-64 visible tokens; the 31 calls cut at the cap show 98-148 reasoning tokens, 21
  of them exactly 148 (the cap minus two visible tokens), so the reasoning distribution is censored
  at ~148 and its tail is unknown. 600 = ~64 visible + ~536 reasoning room, 3.6x the censoring point
  (the earlier estimate was 2.8x the logged prod total, `reports/wave1b/v4-token-breakdown.md`).
  A length finish (or `completion_tokens >= cap`) is never trusted: the turn falls back explicitly to
  retrieval order, outcome `length`, a warning is logged, and `assert_no_length_hits` /
  the report's `a2_length_check` line fail if any call did so (the data is kept either way).
  An empty `selected` list with `finish_reason` stop is a VALID "no exact match": retrieval order,
  `no_exact_match` flag, outcome `empty_selection` (never `parse_error`).
- **B**: RRF order.
- **C**: `variants.build_compact_prompt`: candidates numbered 1..N, `title (12 words) | price band |
  colour`, instructions first (byte-stable prefix), answer = 8 comma-separated numbers, `max_tokens =
  400` (was 200), `temperature 0`. The cap is far above the ~48 the visible answer needs because
  gpt-oss hidden reasoning counts against `max_tokens` even at low effort: day-1 variant A showed
  reasoning censored at ~148 tokens on 31 of 53 calls, so 200 (30 visible + 170) was at risk of the
  same truncation; 400 leaves ~370 for reasoning. Stage 2 reads `finish_reason` and
  `completion_tokens` from the ledger and raises the cap if any C call hits it. The compact system
  prompt is ~150 tokens, below Groq's 1,024-token minimum cacheable prefix, so caching cannot help C
  as designed. Invalid or short output falls back to (or is topped up from) RRF order.
  C does not replay production's colour-diversity swap (`_enforce_colour_diversity`), A does.

### Outcome taxonomy (spec for the later production fix)

Every rerank turn ends in exactly one logged, counted reason (`variants.OUTCOMES`, rates in
`report.rates()["outcome_counts"]`): `ok`; `partial` (a flavour of ok: valid but < 5 picks, topped up
from retrieval order); `length` (finish_reason length, nothing usable; for A2 never trusted at all);
`parse_error` (a complete reply that is not the expected shape, including picks that are all out of
range); `empty_selection` (valid `selected: []` with finish_reason stop: the model says no exact
match, so the turn returns retrieval order with a `no_exact_match` flag and is NOT a parse failure);
`http_error` (the provider call raised); `budget` (day-budget, 3 x 429 or busy stop: the harness
aborts the stage, so it never becomes a data row); `no_llm_call` (pool of <= 5). **Nothing swallowed
is ever called "timeout"** (production's `rerank()` currently logs every swallowed exception as
`timeout` and an empty selection as `parse_error`; the production fix should log these reasons
separately, treat `empty_selection` as valid, and size the cap from the censored reasoning data
above). Day-1 variant A rows keep their original outcome names on disk; the results re-classify
them from the stored raw output (4 of the 35 old `parse_error` rows were `empty_selection`).

### Cards the user sees: the post-rerank replay (`post_rerank.py`)

`rerank()` returns 5, but `search_node` then runs name+colour dedup with backfill, the beach cap and
a chain of gates that DROP cards without refilling them (attribute / theme / accessory /
loungewear gates, the occasion coherence gate with its loungewear / merchandise / athletic-footwear /
haldi-colour gates, the price qualifier, the size-mismatch demotion). Every variant row therefore
carries `final_ids` (the reranker's five) and `cards` (the ids left after the replay, same
production functions in production order). Primary metrics use `final_ids`; `metrics_post_gates`
uses `cards`. Example on the frozen pools: q30 ("blazer", top-5 = pool[:5]) shows 4 cards while a
different pick shows 5, the production blazer 4-vs-5 shape (`tests/test_retrieval_eval_post_rerank.py`).
**Not reproduced:** everything before `rerank()` (the frozen pools already include it), colour-chip
and refinement bookkeeping, the response/rationale nodes, session or ownership logic, multi-turn
state such as `excluded_colours`. On the 53 frozen pools with more than 5 candidates, taking
pool[:5] as the pick, 40 show 5 cards, 8 show 4, 1 shows 3, 3 show 2 and 1 shows 1 (scratch probe,
`apply_post_rerank` over the candidate files). The per-query cause of the low counts (q01, q10, q24
-> 2; q58 -> 1) was not investigated: check them against `search_node` before quoting a card-count
number for those queries.

### Factors on the best two arms (`factors.py`, stage `factors`)

- **F1 sets demoted vs not.** Flag (deterministic from fixture occasion + garment, no model):
  occasion in {sangeet, haldi, mehendi, wedding_guest, festive_diwali} and the stated garment in
  {kurta, kurti, anarkali, anarkali gown, lehenga, saree, sherwani, bandhgala} (no "set", no generic
  "outfit"): the queries where production's single-garment gate actually fires. 8 queries (q01 q02
  q07 q13 q16 q27 q28 q43): small n, so the F1 CI will be wide and the result exploratory. The
  treated arm is the main run on the master-regenerated pool (production's
  `_prefer_single_garment_pool(items, 5)` already applied before rerank by #129: singles first;
  >= 5 singles means sets are dropped from the pool, otherwise demoted behind the singles); the
  base arm re-runs the variant on the frozen pool ("sets not demoted"), only where the two differ
  (6 of the 8). With a single pool directory (no regenerated pools) the treated arm is synthesised
  with `demote_sets` on the frozen pool instead. **Pool-membership changes are judged** with the
  labels every candidate already has (one judging pass over the frozen 20 serves all arms) and an
  nDCG ideal taken from the FULL frozen pool in BOTH arms, so dropping sets can never shrink the
  ideal and flatter the arm; the cost is reported beside it (`pool_loss`: items removed and how many
  of them had label >= 1) with `sets_in_shown_top5` per arm.
- **F2 gender-unspecified.** The 12 fixtures with gender "either": current order vs a pool
  interleaved women's / men's by retrieval rank (start with the gender of the best-ranked gendered
  item; unisex/unknown items keep their positions; the surplus gender follows in rank order). Same
  labels; the variant is re-run on the reordered pool (for B the order is the result).
- An arm is only called when the treatment changes the pool/order; an unchanged pool reuses the
  rep-1 row (`reused`), so no token is spent on a no-op.

### Stability (N = 2)

A and A2 run twice per query (`--reps`, default `DEFAULT_REPS = 2`: rep 1 plus one repeat; cut
from 3 by the architect; rep-major: rep 1 of every arm finishes first). Repeats
are separate cache entries (`rerank-20b-<arm>-r<k>`), so they are real calls; the payload (temperature
0, seed 42) is identical, so any difference is provider-side variance (hidden reasoning). The report
gives, per arm: how many queries show different card counts across repeats (after the post-rerank
replay), how many show a different top-5 set, the per-query detail, and the per-rep mean nDCG@5
(noise floor). Primary comparisons use rep 1 only (one draw per query, like production).

### How truncated reranker output is parsed today (architect item c)

`src/agents/reranker.py:170` calls `llm.generate(..., max_tokens=150, temperature=0)`;
`_parse_selected` (lines 122-145) does `json.loads` on the whole text, else on the first
`{...}` match found by a lazy regex that needs a closing brace. Then (lines 177-181):
`indices is None` -> log `parse_error` -> **return `items[:5]` = retrieval (RRF) order**. There is no
partial salvage: the output is `{"selected": [...], "reasoning": "..."}`, so a cut inside the
reasoning string or the list has no closing brace, parses to None, and the user gets RRF order even
though the picks were already visible in the cut-off text. Only a *valid* JSON with fewer than 5
distinct valid indices is "partial": the LLM picks first, then retrieval order fills (lines 186-194).
If the model spends the whole cap on hidden reasoning and returns empty content,
`GroqClient._chat_one` (`src/llm/client.py:412-425`) returns None, `chat()` moves to gpt-oss-120b
and qwen with the same cap (lines 444-452) and finally returns `LLM_BUSY_MESSAGE` (line 457), which
is not JSON -> same `parse_error` -> RRF order. So in production a cap hit means variant B for that
turn. Pinned by `tests/test_retrieval_eval_variants.py` (`test_truncated_json_falls_back_to_retrieval_order`,
`test_cut_inside_selected_list_also_falls_back`, `test_empty_reasoning_exhausted_output_falls_back`,
`test_complete_json_reorders_and_closed_short_list_is_topped_up`). How often it happens: the V4
report counts 8 of 15 gpt-oss-20b reranker calls at 150 completion tokens
(`reports/wave1b/v4-token-breakdown.md` line 43); my recount of
`reports/wave1b/v4/log_analysis.json` (turn rows, model 20b, input >= 1500) gives 9 of 17
(command: a short script over `turns[].in/out/models`); the filters differ and were not reconciled.
`finish_reason` is not logged, so "at cap" is inferred from `completion_tokens == 150`.

## Pre-registered decision rule (stage 2)

Written by the architect and committed BEFORE any variant result was computed on the consensus
labels (the commit SHA is recorded in the Stage 2 log). It is not changed after results are seen;
any later deviation must be listed explicitly next to the result.

1. **Primary metric:** nDCG@5 on the consensus labels (strict majority of the three judges; the
   median for the no-majority items), one draw per query (rep 1 of every arm), ideal ranking from
   the full labelled pool of the query.
2. **Uncertainty:** paired bootstrap over queries, 10,000 resamples, seed 42, percentile 95% CI
   (`metrics.N_BOOT`, `metrics.SEED`).
3. **Choice:** let *best* be the variant with the highest nDCG@5 point estimate among A, A2, B, C.
   A variant v is admissible when the 95% lower bound of the paired difference (v - best) is
   >= -0.03 (best itself is admissible). Ship the **cheapest admissible variant**: lowest mean
   tokens per turn first (B costs 0), then lowest median latency.
4. **Secondary, reported and NOT used to choose:** precision@5 (labels >= 1, >= 1.5, >= 2) and
   card-count stability across repeats; also the post-gate metrics, the F1 / F2 factors and the
   sensitivity run that excludes tied items.
5. **Reporting:** n per metric and the queries excluded, always. Excluded from the primary
   comparison: the 3 queries with no candidates (q46, q56, q59: production sends them to
   clarify) and the queries whose pool has <= 5 candidates (production skips the reranker, all
   variants show the same cards, so they cannot discriminate). A sensitivity row with all queries
   that have candidates (pools <= 5 included) is reported beside it.
6. **Labels are LLM-consensus labels, not human ground truth** (three model families); every number
   carries that caveat.

reasoning and cached tokens, latency, rate-limit headers), `cache.jsonl` (resumable; keyed by
(judge, query_id, prompt_hash), a rerun makes no duplicate calls), `labels_<judge>.json`,
`variants.json`, `report.json`, `plan.json`. `--resume` is the default behaviour.

### Judge flow and the calibration gate

1. Each Groq judge labels the 20 calibration items (4 synthetic queries x 5 hand-labelled
   candidates, built from the rubric: wrong gender or category = 0, exact match = 2, one colour miss
   or a <= 25% budget overrun = 1). Pass criterion per judge: >= 18/20 exact and none off by two; the
   harness refuses to continue with a judge that fails and says so.
2. Claude labels the same calibration packet. Across all three judges the harness computes pairwise
   kappa (unweighted and quadratic) and Krippendorff alpha. **If any judge pair has kappa < 0.4 it
   stops before the main run and prints the confusion tables and the rubric.** With fewer than three
   judges' calibration labels it also stops (`--allow-partial-gate` overrides, for debugging only).
3. Main run: one call per query with all candidates (cap 1,500 tokens incl. hidden reasoning),
   `reasoning_effort` low for gpt-oss, `temperature` 0, `seed` 42. qwen3.8-27b is sent
   `reasoning_effort: "none"`: UNVERIFIED for this preview model; a 400 from the first call stops the run.
4. Optional: re-judge a random 10 queries with a different shuffle seed to measure stability.

## Quota and day plan (stage 2)

Architect limits, built in as defaults (`common.py`, pinned by `tests/test_retrieval_eval_groq_limits.py`):
judges gpt-oss-120b and qwen3.8-27b only; daily token budget 150,000 per judge model (hard stop,
counted from the ledger per UTC day); the reranker model gpt-oss-20b has a separate 100,000
tokens/day budget because prod canary traffic already uses ~100K of its 200K TPD; **one request per
8 s GLOBALLY** (one clock across both judge models and the reranker, not per model); stop after 3
consecutive 429s; Retry-After and `x-ratelimit-remaining-tokens` honoured. Provider limits as
briefed: 30 RPM, 1K RPD, 8K TPM, 200K TPD per model. The budget pre-check reserves the FULL
completion cap (prompt + `max_tokens`) before each call, so a run can never overshoot the daily
budget (the old 700-token guess could overshoot by ~800 tokens on the 1,500-token judge cap); the
price is that a day stops up to one worst-case call early.

Measured with `python -m evals.retrieval.run --stage plan` (and `python -m evals.retrieval.relabel
--stage plan` for the relabel) at the head of this branch. **Tokenizer: the 3.6 chars/token
heuristic, because tiktoken is not installed here**; it reads ~17% above tiktoken `o200k_base`
(judge prompt mean 1,773 here vs 1,511 in the earlier tiktoken run), so these are conservative;
for qwen the real tokenizer differs again (+-15%). **Completion tokens are ASSUMED, not measured**
(judge 400, calibration 400, A 150, A2 250, C 100, relabel 900 per call); stage 2 replaces them
with ledger medians after the first calls. n = 57 queries with candidates, 53 of which have > 5
candidates (smaller pools skip the reranker).
